# documentation-hosting Specification

## Purpose

Host the c9s documentation site on Cloudflare Workers with automated previews, release-gated production publishing, and custom-domain serving at `c9s.run`.

## Requirements

### Requirement: Cloudflare Workers static hosting

The repository SHALL define a Cloudflare Workers Static Assets deployment that serves the prerendered documentation output from `docs-site/build/client` without requiring a Node.js runtime at the edge.

#### Scenario: Serve prerendered documentation routes

- **WHEN** a reader requests a URL that was generated by the documentation production build
- **THEN** the Cloudflare Worker serves the corresponding static file from the deployed assets directory

#### Scenario: Serve the documentation search index

- **WHEN** a reader loads the browser-side search index endpoint produced by the documentation build
- **THEN** the deployed static assets include and serve the search index without a server-side search service

### Requirement: GitHub Actions Cloudflare authentication

Documentation deployment workflows SHALL authenticate Wrangler using the GitHub repository secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`.

#### Scenario: Deploy with repository secrets

- **WHEN** a documentation deployment workflow runs in GitHub Actions with `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` available as repository secrets
- **THEN** Wrangler can upload preview versions or deploy production without manual Cloudflare dashboard intervention

### Requirement: Independent pull-request documentation pipeline

Pull-request documentation previews SHALL run in a standalone workflow that validates and builds documentation without waiting for the repository Go lint, test, or image build pipeline to complete.

#### Scenario: Preview while code CI is still running

- **WHEN** a pull request receives a new commit and the standalone documentation preview workflow starts
- **THEN** documentation validation and preview deployment proceed without declaring a dependency on the repository code test workflow jobs

### Requirement: Pull-request dual preview URLs

Each successful pull-request documentation deployment SHALL produce two preview URLs: a commit-specific preview URL for the uploaded version and a PR-rolling preview URL aliased as `pr-<number>`.

#### Scenario: Commit-specific preview URL

- **WHEN** a pull-request documentation preview deployment succeeds for a given commit
- **THEN** Cloudflare exposes a versioned preview URL that corresponds to that specific uploaded documentation build

#### Scenario: PR-rolling preview URL

- **WHEN** a pull-request documentation preview deployment succeeds
- **THEN** Cloudflare exposes a stable `pr-<number>` preview alias URL that serves the latest successful documentation build for that pull request

#### Scenario: PR alias updates on new commits

- **WHEN** additional commits are pushed to the same pull request and preview deployment succeeds again
- **THEN** the `pr-<number>` preview alias serves the latest build while the commit-specific preview URL for the new upload reflects the new commit

### Requirement: Pull-request preview comment

The pull-request documentation workflow SHALL post or update a GitHub pull-request comment containing both the commit-specific preview URL and the `pr-<number>` rolling preview URL.

#### Scenario: Comment with two preview links

- **WHEN** a pull-request documentation preview deployment succeeds
- **THEN** the pull request contains a comment listing both the commit-specific preview URL and the `pr-<number>` rolling preview URL

#### Scenario: Update comment on subsequent commits

- **WHEN** a pull request receives additional commits and a new preview deployment succeeds
- **THEN** the existing preview comment is updated rather than leaving multiple competing preview comments

### Requirement: Main-branch rolling preview

Pushes to the default branch SHALL deploy documentation to a stable `main` Workers preview alias and SHALL NOT update production documentation at `c9s.run`.

#### Scenario: Deploy main preview on push

- **WHEN** a commit is pushed to the default branch and the main documentation preview workflow succeeds
- **THEN** Cloudflare serves the built documentation at the stable `main` preview alias URL

#### Scenario: Main push does not update production

- **WHEN** a commit is pushed to the default branch without a release production documentation deploy
- **THEN** the production documentation deployment at `c9s.run` is not updated by that push

### Requirement: Release-gated production deployment

Production documentation SHALL deploy to Cloudflare only from the release workflow after the release code lint, test, and image build jobs succeed. Production documentation SHALL be served at `c9s.run`.

#### Scenario: Deploy on successful release build

- **WHEN** a GitHub release is created, the release lint, test, and image build jobs succeed, and the release documentation deploy job succeeds
- **THEN** the prerendered documentation build is published to the production Cloudflare Worker serving `c9s.run`

#### Scenario: Skip production deploy when release build fails

- **WHEN** a GitHub release is created but a required release code validation or image build job fails
- **THEN** the production documentation deploy job does not publish to `c9s.run`

### Requirement: Deployment validation gate

Preview and production documentation deployments SHALL run `make check-docs` and SHALL run `make build-docs` only after documentation validation succeeds.

#### Scenario: Block deploy on validation failure

- **WHEN** `make check-docs` fails in a documentation deployment workflow
- **THEN** no preview or production Cloudflare deployment is published for that workflow run

### Requirement: Versioned deployment configuration

Cloudflare deployment settings, including Worker name `clabernetes`, assets directory, and preview URL enablement, SHALL be defined in repository-owned configuration consumed by Wrangler.

#### Scenario: Reproduce deployment from repository state

- **WHEN** a maintainer runs the documented Wrangler deploy command against a clean checkout at a release tag
- **THEN** the Worker name `clabernetes` and assets directory configuration used in CI are applied
