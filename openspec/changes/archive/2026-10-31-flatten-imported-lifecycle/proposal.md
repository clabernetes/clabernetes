## Why

Imported containerlab code is executed in four places: the planning worker, the preparation init
container, the connectivity sidecar, and the lifecycle readiness/save boundary. Three of them run
inside the device Pod, where a failed hook is visible only as a Pod that never starts, needs the
Docker-shaped runtime facade, the `docker`/`podman` CLI shims, entropy replay, and a re-render path
whose only permitted difference is the runtime management identity. The planner already exists to
run generation in a sandbox. Preparation can apply its output directly; live observation-dependent
hooks still need the device boundary, as explained in decision D4.

The borrowed contract is also silently incomplete. `PreDestroy` has been part of the imported node
interface since containerlab 0.80 and c9s neither invokes nor reports it: a hook that is never
called emits no recorded operation, so registry-driven conformance cannot fail on it. Any future
method inherits the same invisibility. Until that blind spot is a test, c9s cannot honestly describe
which imported behavior it supports.

## What Changes

- **Preparation applies planned content.** Generated files travel beside the plan as bounded,
  content-addressed artifacts. The controller verifies them and persists immutable Node-owned
  Secrets or ConfigMaps; preparation stages them without evaluating imported code.
- **Resolver DNS is a controller fact.** The manager supplies the resolver set as planning input.
  Runtime template rendering and its alternate-digest record are removed.
- **Live hooks retain imported behavior.** Post-deploy, readiness, save, and endpoint hooks depend
  on live device observations and direct device I/O. They remain in the Pod, with the runtime
  facade and CLI shims. Initialization and deployment reconstruct state in scratch space, then
  hand over to the live runtime without comparing recorded construction streams. Construction
  must preserve staged and device-saved content; target-worker preflight checks still run.
- **Imported-hook coverage guard.** Every imported interface method is classified as exercised,
  refused, or unused. Refusals are attributed to the linked kind implementations and surfaced
  in conformance; native equivalents such as topology exec are not blanket refusals.
- **Private artifact transport.** Both pooled and disposable workers return generated bytes over
  Kubernetes exec streams, so private keys do not enter Pod logs. The controller persists the
  validated artifacts before publishing a compact cache record.
- **BREAKING (internal plan schema):** `SchemaVersion` becomes `v1alpha2`; `PlanArtifact` replaces
  generator-sourced files. Imported action kinds remain. CRDs and the containerlab pin do not change.

The initial proposal to flatten every hook into plan steps was superseded by design decision D4.
It would require device protocol knowledge or native reimplementation of the imported hooks.

## Capabilities

### New Capabilities

None. This change removes preparation-time evaluation and adds verification of imported coverage
and artifact integrity.

### Modified Capabilities

- `device-planning`: generated content and resolver inputs are fixed during planning; imported
  interfaces have an explicit coverage inventory.
- `direct-device-runtime`: preparation applies content; live hooks use isolated construction
  without operation-stream comparison.
- `direct-runtime-conformance`: unsupported imported behavior is reported per affected kind.

## Impact

- `internal/deviceplan`: adapter, post-deploy and readiness recorders, save, preparer, codec, and
  plan types (`SchemaVersion`, `FileSourceGenerator`, imported action kinds).
- `internal/directruntime`: imported application/endpoint runtime facade, runtime-CLI shims,
  lifecycle, readiness, and connectivity hook execution.
- `controllers/node`: plan artifact persistence and payload references; worker artifact garbage
  collection.
- `internal/conformance`: hook-coverage inventory and gate.
- `internal/directpod`: rendering of the plan artifact sources; no Pod-shape change is expected.
- Docs: `docs/architecture.mdx` and `docs/concepts/containerlab-differences.md` describe in-Pod hook
  execution today.
- No API/CRD change, no chart or RBAC change, no containerlab version bump. Existing e2e suites remain acceptance gates; regression tests cover the new artifact and
  transport boundaries.
