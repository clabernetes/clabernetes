## Context

The planning worker exists so imported containerlab code never runs in the long-lived manager: it
executes with a recording runtime inside a fresh, deadline-bounded subprocess and emits a
runtime-neutral plan. That boundary is sound. But the same imported code is executed again in three
other places:

1. the **preparation init container** re-evaluates the imported registry (`Preparer.Prepare` ->
   `evaluateInWorkspace`) to reproduce generated files, replay package entropy, and re-render
   artifact content with the Pod's runtime management identity (`renderRuntimeManagementArtifacts`,
   `runtime-artifact-digests` record);
2. the **connectivity sidecar** replays `ActionImportedDeployEndpoints` hook execution against the
   device network namespace (`RunDeployEndpoints`);
3. the **lifecycle/readiness boundary** replays `ActionImportedPostDeploy`, imported readiness
   checks, and `SaveMethodImported` (`RunPostDeploy`, `CheckReadiness`, `RunSave`).

Supporting that replay is the bulk of the boundary's machinery: the Docker-shaped
`importedApplicationRuntime` facade (~34 fail-closed methods), the `docker`/`podman` runtime-CLI
shims, operation-drift validation, entropy sessions at two execution sites, and the `FileSourceGenerator`
plan source that means "the Pod produces this file by running imported code".

Two concrete defects motivate the change:

- The plan never carries generated bytes (`FilePlan.SourceKind` is `Payload | Generator |
  Certificate | Empty`), which is *why* preparation must re-run imported code at all.
- The borrowed interface grows silently. `PreDestroy` was added to the imported node interface in
  containerlab 0.80; `grep -rn PreDestroy internal/ controllers/` is empty. A hook that is never
  invoked emits no recorded operation, so registry-driven conformance cannot report it, and the
  `device-planning` spec's claim that verification fails for any unrepresented generic operation
  does not hold for methods c9s never calls.

Constraints: no containerlab removal or kind porting in this change; no CRD/API change; the pinned
containerlab version stays 0.81.0; existing e2e suites are the acceptance gate; generation remains isolated in planning; observation-dependent hooks retain the live device boundary.

## Goals / Non-Goals

**Goals:**

- Preparation stages and verifies accepted content without evaluating imported code.
- Generated files retain digest, mode, ownership, xattr, size, and device-modification protections.
- Host deployment requirements are checked on the target worker before application startup.
- Observation-dependent hooks retain their imported implementation; scratch construction cannot
  overwrite accepted artifacts or device-saved configuration.
- Every imported interface method is classified as exercised, refused, or unused, with derived
  per-kind attribution for unsupported behavior.
- Remove redundant construction-stream comparisons and preparation-time rendering.
- Generated private material travels over private exec streams and is persisted only in Secrets.

**Non-Goals:**

- Removing the containerlab dependency or porting kind knowledge into c9s.
- Changing the planner sandbox or pool capacity. Disposable and pooled workers share private exec
  result handling; disposable workers retain their projected payloads.
- Changing Pod shape, CRDs, RBAC, charts, exposure, connectivity, or management mesh behavior.
- Improving or re-designing kind behavior; this change must be behavior-preserving apart from the
  two documented exceptions below.

## Decisions

### D1: Preparation applies accepted content

Preparation MUST NOT construct a registry or evaluate imported hooks. It reads the plan, stages
its content, and verifies digests and metadata. Post-deploy, readiness, save, and endpoint hooks
remain at the live boundary under D4; imported construction uses scratch paths until the live hook
runs. The initial single-execution-site goal is superseded by this scoped contract.

### D2: Generated content travels as content-addressed plan artifacts

A generated file becomes a `FilePlan` whose content is a plan artifact: digest-named, immutable,
mode/ownership/xattr metadata preserved (already recorded by `artifact_metadata_linux.go`), with a
declared total size bound per plan. `FileSourceGenerator` is removed; source kinds become `Payload`,
`PlanArtifact`, `Certificate`, and `Empty`.

Storage reuses the payload model rather than inventing one: bytes are persisted by the controller in
digest-named, owner-referenced objects that preparation already knows how to fetch and verify.
Sensitive artifacts (certificate/key material a hook writes) MUST use the Secret-backed form and MUST
NOT be copied into a ConfigMap payload.

*Alternatives rejected:* inline bytes in the plan ConfigMap (1 MiB limit, mixes sensitive and public
content, invalidates the plan object on every content change); OCI artifact (new registry dependency
and pull path); planner scratch volume handed to the Pod (node affinity coupling, no immutability).

### D3: Resolver DNS becomes a controller fact, not a Pod fact

The `device-planning` spec already forbids synthesizing a management identity from the Pod address and
allows exactly one runtime contribution to management rendering: Pod-resolver DNS discovery
(`RuntimePodDNSServers`, consumed by `completeRuntimeManagement`). That single residual fact is what
forces `renderRuntimeManagementArtifacts`, the second in-Pod evaluation, and the
`runtime-artifact-digests` record.

DNS resolution moves to the manager: the controller resolves the resolver set once (cacheable, and
equal in practice to what device Pods receive under the cluster's own DNS configuration), places it
in the planning input as controller-allocated data, and the planner renders generated configuration
from it. Preparation no longer reads the Pod's `resolv.conf`, and `renderRuntimeManagementArtifacts`
with its digest record is deleted. The device's own `resolv.conf` is left to Kubernetes exactly as it
is today; this change aligns the *generated package configuration* with plan data, not the Pod's DNS
policy.

*Alternative rejected:* keep Pod-scoped DNS and substitute the server list into planned bytes during
preparation. It preserves a runtime divergence path, a per-Pod digest record, and a substitution
mechanism whose only justification is the value we can resolve one layer up.

*Alternative rejected:* placeholder tokens inside planned bytes. Package templates cannot emit our
token, and it turns a typed identity question into string surgery over vendor configuration.

### D4: Observation-dependent hooks stay at the in-Pod boundary without stream comparison

Flattening post-deploy, readiness, save, and endpoint hooks into plan steps was evaluated and
rejected on evidence:

- their control flow depends on live device observations (`srl.Ready` polls `RunExec` output for
  `"running"` until a five-minute deadline; `sros.PostDeploy` runs a health loop, TLS bootstrap,
  version detection, and a conditional config commit), and the planning recorder answers exec with an
  empty result, so plan-time recording either spins to the deadline or bakes in the wrong branch;
- 43 kind packages perform direct device I/O that bypasses the recorded runtime entirely
  (`clabnetconf`, scrapli, `SpawnCLIviaExec`), and the planning worker is deny-all egress by design,
  so those hooks cannot run there at all;
- a faithful step list would therefore require either fabricated per-command outputs (device
  protocol knowledge in c9s) or a native reimplementation of each hook, which is the separate
  kind-ownership change.

The hooks stay in the Pod against the live container. Initialization, preparation, and deployment
still reconstruct their state in scratch space; this change removes stream comparison, not those
constructor calls:

| today | after |
| --- | --- |
| reconstruct the Node graph with a recorder, then compare the recorded container inventory and deployment operations against the accepted plan, then switch to the live runtime | reconstruct in scratch space, verify the target container runtime IDs, then switch to the live runtime |
| readiness container IDs re-derived and diffed against the plan during every hook | removed |
| `verifyReplayedDeploymentOperations`, `sameReplayedDeploymentOperation`, `replayedDeploymentOperation`, `deploymentReplayError`, `verifyReplayedContainers`, `verifyReplayedReadinessInventory` | deleted |

The accepted plan still binds the hook to its input by digest (`ValidatePlanInputIdentity`), so the
hook runs against exactly the configuration planning produced. What is given up is the second-order
check that the rest of the Pod's construction stream matches the plan byte-for-byte. A small
inventory check remains at the shared post-deploy/endpoint boundary: the target Node's reconstructed
container runtime IDs must equal the planned IDs, independent of creation order. Missing, extra,
or different IDs fail before switching to the live runtime. This uses the already-recorded
construction inventory; it does not repeat planning, compare operations, or observe actual
Kubernetes container state.

*Alternative rejected:* typed `Capture`/`When` plan steps plus a c9s interpreter. It is implementable
for exec-only hooks (save on srl/ceos/frr/linux/sonic_vm) but cannot express hooks that dial the
device or loop on its output, and a per-kind split would put kind identity back inside the boundary.

### D5: The coverage guard has two halves

1. **Interface-method classification.** Reflect over the imported interfaces the adapter relies on
   (`nodes.Node`, `nodes.NodeOverwrites`, and any other interface c9s type-asserts) and compare the
   method set against a committed classification: `exercised`, `refused` (with reason and affected
   kinds), or `unused` (with reason). An unclassified method fails unit verification, and so does a
   classification that claims `exercised` while the adapter no longer calls it.
2. **Hook-action preservation.** Every imported action kind that remains in the plan must name a hook
   the hook boundary actually invokes, and no action may instruct a boundary to replay construction
   operations. This is checked structurally, in the style of the existing `kind_agnostic_test.go`
   source scan.

The inventory is reported by conformance, so a `refused` method appears as a reported incompatibility
rather than a silent pass; kinds gated by e2e must be `exercised`.

### D6: Sequencing is guard, then plan-borne bytes, then replay deletion

Each step is independently shippable and keeps e2e green:

1. guard + inventory (no behavior change, produces the work list);
2. artifact bytes + preparation flattening (removes `FileSourceGenerator`, entropy, registry from prep);
3. replay deletion at the hook boundary (construction recorder hands over to the live runtime); the
   imported hook execution, runtime facade, and runtime-CLI shim stay, because observation-dependent
   hooks cannot leave the Pod.

Schema: `SchemaVersion` is bumped once, in step 2, and again in step 3 if the step vocabulary requires
it; the controller's existing plan identity check forces regeneration of stale plans.

## Risks / Trade-offs

- **Operation-stream drift is no longer checked**: input identity and target container runtime
  IDs are verified before post-deploy/endpoint hooks, but those checks do not establish equivalence
  of the construction operations. Vendor e2e and conformance remain the evidence for behavior.
- **Generated content grows the plan** (bytes that used to be produced in-Pod now persist) -> explicit
  per-plan size bound, reuse of the existing bounded payload transfer path, and garbage collection of
  superseded artifact objects alongside plan ConfigMaps.
- **Sensitive generated files could leak into a ConfigMap** -> the plan artifact kind is chosen from
  the producing hook's declared sensitivity, and a test asserts certificate/key sources never render
  as ConfigMap payloads.
- **Manager-resolved DNS differs from what a device Pod would have seen** (for example a node-level
  `resolv.conf`, or `dnsPolicy: Default`) -> the management and SR Linux DNS e2e suites are the gate;
  a configuration whose generated DNS cannot be resolved consistently fails planning with a named
  diagnostic instead of reintroducing in-Pod rendering.
- **The guard is satisfiable dishonestly** by marking everything `refused` -> refusals must name
  affected kinds and surface in the compatibility report, and every e2e-gated kind must be
  `exercised`.
- **Rollback**: reverting the manager image restores the previous behavior; plans are regenerated on
  the next reconcile and no cluster state is migrated.

## Migration Plan

1. Land the coverage guard and inventory (no runtime behavior change) and record the current
   classifications, including `PreDestroy`.
2. Persist generated artifacts and remove package evaluation, entropy, and runtime-identity re-render
   from preparation; bump `SchemaVersion`.
3. Keep observation-dependent hooks, the facade, and CLI shims. Isolate construction in scratch
   space and remove construction-stream comparison and the `runtime-artifact-digests` record.
4. Update `docs/architecture.mdx`, `docs/concepts/containerlab-differences.md`, and the spec text that
   describes in-Pod hook execution.

Validation per step: `go test ./internal/... ./controllers/...`, `make test`, `make test-race` for the
sidecar path, `make lint`, `make verify-generated` (plan schema/status), `make check-docs`, and
`make test-e2e-local` covering the suites in `.github/workflows/e2e.yaml` (SR-SIM requires
`SRSIM_LICENSE` and GHCR auth; a run without it is incomplete evidence).

## Open Questions

- Which kinds embed resolver DNS in generated configuration today, and is manager-resolved DNS
  byte-equivalent for them in the existing e2e clusters?
- Which of the 43 device-dialing hooks should be reimplemented natively first when the kind-ownership
  change lands, so the in-Pod imported boundary can eventually disappear?
- Does any imported hook request image metadata or certificates mid-hook in a way that changes once
  the hook runs at plan time only? (The session protocol already resolves these at plan time, so this
  is expected to be a no-op, but it must be confirmed against the recorder logs.)

## Implementation Notes (task group 2)

- Generated artifacts travel as `ArtifactContent` beside the plan and are persisted as one
  digest-named immutable object per artifact (Secret, because planning already marks generated
  content sensitive). Preparation reads them from the projected payload mount, verifies the digest,
  and stages them, so it has no registry, entropy, or evaluation path left.
- Extended-attribute values cannot be reproduced from a digest, so a value travels with the
  artifact and is stored beside its content (`xattr-<base64url name>`). Directory artifacts that
  carry only metadata are supported the same way, with an identity derived from the attribute
  digests rather than from content.
- Resolver DNS is resolved once in the manager (`/etc/resolv.conf`) and rides the planning input as
  `ManagementInput.ResolverServers`. The completion applies only to package-visible configuration:
  container DNS policy still comes from the declared topology, captured before completion.
- A plan whose generated artifact object is missing invalidates the cached planning result, so a
  later reconcile plans and persists it again instead of applying against absent bytes.
- The non-session planning worker (`Worker`) now refuses plans that carry generated artifacts: the
  bare plan frame cannot deliver bytes, and it must not look like a complete result.

## Validation Evidence

- Unit: `make test` and `make test-race` green (1193 tests, 15 skipped); `make lint` 0 issues.
- Cluster: the full e2e matrix was run against an existing cluster with every opt-in gate enabled
  (cEOS, Cumulus, vJunos-router, VM-backed vrnetlab kinds, planner-pool reuse/scale/mixed-vendor,
  per-host startup admission, and an environment-owned conformance bundle).
- Enabling those suites exposed four harness defects, which were fixed in the tests rather than
  reported as product findings: a stray space in the vJunos-router default image that mangled the
  manifest, an exact SR-SIM container count that had rotted, a hardcoded KinD-only `kube-dns` Service
  name, and a 200-Node poll plus global-admission setup that needed transport retries and a policy
  warm-up. The procedure and its caveats are recorded in `AGENTS.md`.
