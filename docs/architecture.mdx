## Overview

clabernetes is a collection of kubernetes custom resources and controllers that reconcile those
resources. The ultimate goal of the controllers is to render a network topology in the cluster:
one device Pod per (containerlab) node running the actual network-device image as a regular
application container, network node interfaces stitched together across pods, and the management
interfaces of the nodes exposed.

There is no nested runtime: no Docker daemon inside the Pod, no containerlab executable, and no
image import path. The kubelet pulls and runs every device image natively, and Kubernetes owns
device lifecycle, logs, resources, and status. Kind behavior -- defaults, generated files,
lifecycle commands, readiness -- comes exclusively from an unmodified, pinned containerlab Go
module whose hooks run against recording boundaries, so a containerlab module bump admits new
kinds without any clabernetes kind code.

## The Primary API: Nodes and Links

A `Node` custom resource represents a single containerlab node -- its spec is simply what a
human would write for that node in a containerlab topology file (flat, verbatim containerlab
vocabulary). A `Link` custom resource represents a single wire between two nodes. That's the
whole authoritative api: apply Node and Link objects and the controllers render a running,
wired lab -- no Topology object required.

The object name of a Node *is* the containerlab node name: the device pod hostname and the
node's services derive from it, which also means the **namespace is the topology boundary**.
Everything operational is controller-stamped into the statuses: expose port allocations and
readiness on Nodes, tunnel id allocations on Links. Deployment *policy* -- expose behavior,
image pull defaults, primary-container resources, scheduling, persistence, probes -- lives on
`NodeProfile` (the retained CRD name for reusable direct-workload policy). Each Node can
explicitly reference one same-namespace profile through `spec.profileRef`; an omitted
reference uses global Config defaults, while a missing explicit reference prevents realization
instead of silently falling back. Device privilege, capabilities, devices, and other kind-owned
container requirements are *not* profile policy: they come from the imported package's plan.

The primitive objects are bounded: a Node grows only with its own definition and payload, a
Link contains one wire, and each device Pod's connectivity helper watches only Links
terminating on its own Nodes (server-side field selectors require Kubernetes 1.31+). This
removes the single authoritative aggregate-object ceiling; it does not imply arbitrary runtime
scale because API-server capacity, controller throughput, and total object count remain finite.

`Topology` remains a supported, backward-compatible auxiliary resource. Its existing
`connectivity`, `expose`, `deployment`, `imagePull`, and `statusProbes` fields are accepted and
compiled into primitive resources. Because a Topology still embeds the whole source definition,
large labs should use clabverter's direct primitive output instead of persisting a Topology.

## Components

### Controllers & Custom Resource Definitions

The "brains" of clabernetes is the manager deployment which runs three cooperating controllers:

- the **node controller** turns every Node (or `network-mode: container:<primary>` group of
  Nodes) into one Recreate Deployment of a direct device Pod, a per-node "fabric" service
  (`<name>-vx`, headless peer discovery for cross-worker wires), an expose service (`<name>`),
  one headless service per declared network alias, and an optional PVC -- and stamps
  readiness/allocations into the Node status. Before rendering, it resolves image metadata and
  runs planning (below); a Node whose plan fails stays failed with a structured diagnostic and
  never mutates the last successfully applied workload.
- the **link controller** validates Links and allocates cluster-wide tunnel ids into their
  statuses (tunnel ids become the VXLAN VNIs of in-Pod fabric tunnel endpoints; the allocation
  space is global, not per-namespace, so no two wires anywhere share a VNI).
- the **topology controller** is the optional convenience layer: it *compiles* a Topology
  (a containerlab file plus knobs) into NodeProfile/Link/Node objects -- expanding
  topology defaults/kinds/groups into each node so every emitted Node is self contained --
  prunes emitted objects that fall out of the definition, protects them from drift, and
  aggregates fixed-size counts and readiness back into the Topology status. Profiles and Links
  are reconciled before Nodes.

The compiler normally emits one shared NodeProfile and places its explicit reference on
every Node. A distinct per-node workload resource policy produces a complete dedicated profile,
not an inheritance chain.

Compilation fails closed: any unrecognized or unrepresentable baseline field fails before
resource creation with sorted structured diagnostics naming every unsupported field and
location. Fields the direct runtime deliberately rejects (`runtime`, `auto-remove`, `pid-mode`,
`cgroupns-mode`, `cpu-set`, `stages`, `credentials`) each fail with a diagnostic stating why.
Only constructs whose loss cannot change lab behavior inside the cluster are accepted with a
warning instead: Docker-only management-network fields (`mgmt.network`, `mgmt.bridge`, MTU,
external access, driver options) and the host half of Docker-style port pinning. Explicit
`veth` links may use brief `node:interface` endpoints or equivalent structured
`node`/`interface` mappings; empty or malformed endpoint values fail before Link resources are
emitted.

### Planning

Imported containerlab code mixes intent with side effects, so kind hooks never run inside the
long-running manager. The node controller instead launches a short-lived, locked-down and
deadline-bounded **planning Pod** per plan input. Inside it, the imported registry
and node hooks run against a generic recording runtime and a disposable workspace: container
creation, files, mounts, lifecycle, exec, namespace, and interface operations are *recorded*
rather than performed, and the result is a deterministic, runtime-neutral **device plan**.

The plan's image configuration comes from a registry **metadata resolver** in the manager that
fetches only manifests and config blobs (never layers) using same-namespace pull Secrets and
the controller-only `Config.spec.imagePull.registryMetadataTrust` policy. The kubelet performs
the only real image pull, and readiness fails on a material digest mismatch between the planned
image and the kubelet-reported `imageID`.

Accepted plans are stored in immutable, digest-named, owner-referenced ConfigMaps that contain
no secret bytes; payloads and certificates ride as referenced objects. Each cold plan owns one
bounded mutable connectivity-revision ConfigMap so live-capable Link changes update interfaces
without rolling the Pod.

### Direct device Pods

Each rendered Pod runs, in order:

1. a **preparation init container** that re-runs the imported deterministic file generation
   against its mounted payload/certificate inputs, verifies every planned path, mode, and
   digest, and stages artifacts into plan-scoped volumes -- rendering generated configuration
   with the runtime-completed management identity so package templates emit the real
   management address, prefix, and gateway;
2. a **restartable privileged connectivity init-sidecar** whose startup probe gates device
   start until the accepted cold-start interface set exists. It stays running to reconcile
   live Link changes, invoke imported endpoint hooks, and publish connectivity readiness; and
3. one **regular application container** per grouped logical Node or planned chassis component,
   running the unmodified device image. Kubernetes-native image pull policy, pull Secrets,
   environment, users, ports, resources, devices, capabilities, privilege, seccomp/AppArmor,
   sysctls, tmpfs, shared memory, and DNS all map from the plan onto native Pod fields.

A standalone Node has one Deployment/Pod; `network-mode: container:<primary>` adds application
containers to the primary's Pod; a component-based node (i.e. a distributed SR-SIM chassis)
expands into card containers that are directly visible as application containers of one Pod
with validated namespace ownership. Container names are deterministic DNS labels derived from
logical Node and component identity, so `kubectl logs` and `kubectl exec` target the actual
device container (`-c` selects components).

VM-backed kinds stay ordinary application containers running their packaged qemu/vrnetlab
entrypoint; the plan grants `/dev/kvm`, tap access, and resources, and clabernetes does not
launch the VM itself.

### Inter-Node Connectivity

The device always sees a plain interface leg -- every kind tolerates that, including kinds
that adopt the interfaces presented to them. All connectivity is realized by the Pod's own
privileged **connectivity sidecar**; no node-resident agent exists. Before any device container
starts, the sidecar preserves the CNI interface under a sidecar-owned name (`c9s0`), so the
Kubernetes underlay survives whatever a device does to the interfaces it is shown.

Cross-pod wires terminate inside the Pod on that preserved underlay: each endpoint is a veth
leg stitched (tc mirred, checksums materialized) to an in-Pod VXLAN VTEP whose VNI is the
Link's allocated tunnel id. Peer discovery uses the per-node headless
fabric service (`<remote node>-vx.<namespace>...`), which publishes the current Pod address
even before readiness; rewiring and Pod rescheduling converge on the sidecar's reconcile tick.
Same-Pod, loopback, and local veth state stays inside the Pod sandbox and is removed
automatically with it. Host Links (`host:<interface>` endpoints) are veth pairs whose
worker-side end the sidecar places through a read-only worker network-namespace handle
(mounted only when the topology declares host Links); because a veth pair dies with either
end, forced Pod deletion leaves no worker residue and nothing needs sweeping.

### Management and DNS

Management identity is always addressed with containerlab semantics: every node's management
address is controller-allocated -- from the operator's management policy (profile `mgmt`
subnets, static `mgmt-ipv4`/`mgmt-ipv6`), or from containerlab's default management subnet
(`172.20.20.0/24`, gateway at the first usable address) when no policy is declared. The
sidecar interposes a synthetic management interface carrying that address before the device
starts: the device adopts it exactly as it would a physical management port, a sidecar-owned
policy routing table keeps Kubernetes transport immune to device rewrites of the main table,
and an nftables translation table (hooked ahead of anything a device programs) SNATs outbound
management traffic to the Pod address and DNATs declared ports from it, so Service exposure
keeps working. Management configuration renders at plan time through each kind's own imported
templates using the allocated address, prefix, and gateway.

The management subnet is one shared L2 domain across the whole topology, exactly as on
containerlab's management network: a device dialing a peer's *management address* (a hardcoded
telemetry target, a syslog collector, plain ping) reaches the peer device itself, any protocol,
both directions. Each Pod bridges its management legs onto a management VXLAN tunnel endpoint
riding the same substrate as Link fabric, with peers discovered through a namespace-scoped
headless Service (`c9s-management-mesh`) -- so nodes joining or leaving the namespace converge
on the sidecar's reconcile tick without restarting any Pod. The management *gateway* stays
strictly Pod-local: every Pod answers the gateway address itself with one deterministic
identity, and gateway traffic never crosses the mesh. Lab members also resolve each other by
node name through namespace-local Services; declared `aliases` add extra headless Services
bound to the same Pod.

### Exposing Nodes

Ports listed in a node definition (plus a sensible default set unless auto-expose is
disabled) are allocated into the Node status and exposed through a per-node service --
LoadBalancer flavored by default -- targeting the device Pod's ports directly. The assigned
address is reflected back into the Node status.

### Status and readiness

The node controller reads init/application container status directly and maps it back to each
logical Node using applied plan identity and UID checks, so a stale Pod cannot update a
replacement Node. OCI image healthchecks and declared `healthcheck` contracts translate into
container startup/readiness behavior; profile `statusProbes` add TCP/SSH checks. Failures
surface as bounded Node conditions and Kubernetes Events naming the logical Node, plan digest,
and failing typed action.

### Clabverter

While the goal of clabernetes is to take a containerlab topology and "directly" translate it
into a running clabernetes topology in your cluster, there are a few things that cannot be
translated directly. Chief among those is startup configurations or any other type of file
that you would like to mount to some path on one of your nodes. Containerlab solves this
problem by letting you run binaries on your local machine and then mounting/copying files
relative to where you ran the command into their appropriate location(s).

As clabernetes is not running on your machine, and you only interact with it via the
kubernetes api, we don't have any way to automagically copy or mount any files from your
machine.

To work around this, the "clabverter" tool was created -- this is a very simple cli tool that
can be pointed at a containerlab topology (either locally or at a URL). This tool determines
if any files would be mounted when using this topology file, and if so renders kubernetes
configmaps containing the file contents and a Topology that appropriately mounts them into
the pods.

clabverter can also skip the Topology object entirely: `--emit-crs` renders the primitive
NodeProfile/Link/Node manifests directly, using the same compile and render pipeline as the
in-cluster compiler (without Topology owner references). This is the preferred path when the
aggregate source Topology would be too large to persist. Both paths validate identically and
fail with the same sorted diagnostics before anything reaches the cluster.
