C9s now pins [containerlab 0.81.0](https://https://containerlab.dev/rn/0.81/). The [kind-specific](https://containerlab.dev/manual/nodes/#kind-specific-config) config model that 0.80 introduced is fully adopted.

## Kind-specific config

Containerlab 0.80 replaced the `CLAB_*` environment variables with kind-specific node keys, and
c9s adopts the same model. Kinds that need more than the generic node settings are now configured with their "specific" keys on the node config level. Like the `breakouts` in the example below:

```yaml
topology:
  nodes:
    cumulus:
      kind: nvidia_cumulusvx
      image: ghcr.io/clab-labs/nvidia_cumulus:5.16.5-boxen
      port-count: 64
      breakouts:
        - port: 1..20
          channels: 4
```

### Removed: node `extras`

The node `extras` field is gone, following containerlab's
[kind-specific config migration](https://github.com/srl-labs/containerlab/pull/3458). Everything
it carried was either a kind config key or dead:

| Old `extras` key | Use instead |
| --------- | ------------- |
| `extras.frr.daemons` | [`daemons`](/docs/guides/frr#daemons), a kind config key of the `frr`/`frrouting` kinds |
| `extras.ceos-copy-to-flash` | `copy-to-flash`, a kind config key of the `arista_ceos` kind |
| `extras.k8s_kind.deploy.kubeconfig` / `.wait` | `kubeconfig` / `wait`, kind config keys of the `k8s-kind` kind |
| `extras.srl-agents` | Nothing, containerlab removed the agent copy it fed (nothing consumed it in c9s either) |
| `extras.mysocket-proxy` | Nothing, mysocketctl is gone |

Move the keys to the node definition in the Topology
[`definition:`](/docs/crd/topology#spec-definition) and drop them from any hand-authored
[`Node`](/docs/crd/node) manifest: a Topology definition that still carries `extras` fails
compilation with the migration pointer containerlab deploys with, and a `Node` manifest that
sets the removed `spec.extras` field fails server-side field validation on `kubectl apply`.

## Cumulus VX breakout ports

`nvidia_cumulusvx` nodes can generate a breakout port layout with the `port-count` and
`breakouts` kind config keys, producing the `/config/ports.conf` the vrnetlab image uses to
rename selected ports into the Cumulus breakout form `swpNsM`. Link endpoints use the lane
names:

```yaml
topology:
  nodes:
    cumulus:
      kind: nvidia_cumulusvx
      image: ghcr.io/clab-labs/nvidia_cumulus:5.16.5-boxen
      port-count: 2
      breakouts:
        - port: 1
          channels: 4
  links:
    - endpoints: ["cumulus:swp1s0", "client:eth1"]
```

The [Cumulus example](https://github.com/clabernetes/clabernetes/tree/main/examples/basic) and
the E2E suite boot a breakout lab and prove the dataplane across two lanes, including guest
forwarding between them.

## FRR node added to the end-to-end test suite

The `frr` kind is a first-class citizen in containerlab 0.80, and c9s now covers it in the
always-run E2E suite: two FRR nodes boot as direct device Pods with containerlab's generated
`/etc/frr` configuration, the wire interfaces take their addresses from the startup
configuration, an OSPF adjacency forms across the fabric link, and OSPF-learned routes carry real
traffic. See the [FRRouting guide](/docs/guides/frr) for an example and the daemon selection
syntax.

## Management networks

Containerlab 0.80 added macvlan management networks, containerlab IPAM, Tailscale management
integration, and multiple management networks. c9s realizes a single cluster-agnostic management
network per namespace, so:

- The new Docker-only `mgmt` fields (`driver`, `ipam`, `macvlan-*`, `tailscale`) are accepted and
  ignored with a warning, like the existing `network`, `bridge`, and `mtu` fields.
- A single-entry `mgmt:` list is carried as-is; more than one management network fails
  compilation until a per-network management plan exists.
- Node `mgmt-net` selections are accepted and ignored.

## Fixes

- The mesh neighbor inventory ignores the generic rtnetlink notification that kernels before
  6.13 emit after every self FDB change on a VXLAN device. It carries only the MAC — no
  destination — so caching it produced a forwarding entry the kernel refuses to delete,
  `clabwire` exited on the next reconcile pass, and every restart dropped the Pod's wire
  carrier. On 6.1 workers this crash-looped every multi-link Pod; affected labs now converge.

## Planner compatibility

Plans are tied to the linked containerlab module version and registry digest, so the first
reconcile after an upgrade re-plans every Node once. Devices restart with their pods as usual.
