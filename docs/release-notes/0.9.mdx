<Callout type='warn'>

This release replaces the nested launcher runtime with the direct device runtime and removes
launcher-era API fields.

**Due to the massive refactoring that has happened, upgrading from older release is not planned. You will have to uninstall the old version and start afresh.**

</Callout>

0.9.0 changes how labs run, connect, and recover. Since 0.8.0, devices have become native
Kubernetes containers, management networking has gained configurable addressing and a routed
mesh, and links propagate carrier loss across workers. Saved device configuration can survive
Pod replacement, while reusable planners and startup admission controls support larger labs.

## The direct device runtime

Every network device now runs as a regular application container in a c9s-managed Pod. The
launcher image, the Docker daemon inside the Pod, the containerlab executable, image import,
and nested container discovery are gone. What this changes in practice:

- `kubectl logs`, `kubectl exec`, resource limits, and Pod status address the actual device
  container. Chassis cards and grouped nodes are visible application containers of one Pod.
- The kubelet performs the only image pull, with native `imagePullPolicy` and
  `imagePullSecrets`. c9s resolves only registry metadata (manifests and config blobs) and
  fails readiness if the running image diverges from the planned digest.
- Kind behavior comes from the pinned containerlab 0.79.0 Go module. Its hooks run in isolated
  planner subprocesses and produce a deterministic device plan; four reusable planner workers
  serve the installation by default. Unchanged accepted plans skip execution. See
  [Planning and startup at scale](#planning-and-startup-at-scale).
- Each device Pod boots through a preparation init container that stages and digest-verifies
  every generated and payload artifact, and a restartable privileged connectivity init-sidecar
  that gates device start on the accepted cold-start interface set and applies live Link
  changes.

The runtime replacement is covered in [#307](https://github.com/clabernetes/clabernetes/pull/307).
The containerlab update and extraction of the reusable `compiler` Go package are in
[#313](https://github.com/clabernetes/clabernetes/pull/313).

## Links, carrier loss, and recovery

Each device Pod's privileged connectivity sidecar realizes its own links; no node-resident
agent is installed. Cross-Pod frames ride the fabric wire, a sidecar-to-sidecar UDP transport
keyed by the Link's namespace-unique wire id, while same-Pod, loopback, and local veth state
stays inside the Pod sandbox. The device always sees a plain veth interface. Wire semantics
(L2 point-to-point, MTU intent, carrier propagation, live rewires, cleanup, rescheduling) are
preserved. The `connectivity` field is removed from Topology and Link specs: there is exactly
one realization, and the experimental slurpeeth transport is retired.

### Link loss detection

Shutting down or removing an interface at one end makes the peer see loss of carrier
(`NO-CARRIER` / `LOWERLAYERDOWN`), while its interface stays administratively up. Protocols
can react to the cable failure instead of waiting for their hold timers. If a Pod dies,
heartbeats take its peer links carrier-down within a few seconds; carrier returns when the
replacement endpoint converges. Carrier messages, heartbeats, and frames use the same UDP
socket and network path. This detects endpoint/path loss, but small heartbeats can still pass
through a path that drops only large packets.

Packet loss stays visible: the wire never retransmits a dropped frame. It fragments jumbo
frames to fit the Pod network and either reassembles the complete frame or drops it. This
allows the default 9500-byte link MTU across typical 1500-byte cluster networks without
lowering the lab's link MTUs. VLAN tags are preserved; full-size QinQ payloads need four extra
bytes of link MTU. Losing any fragment loses the frame, so large frames amplify underlay loss.

### Changing links in a running lab

Kinds whose plans support `Live` link changes receive connectivity updates in place. For
non-live `Restart` and `Recreate` changes, c9s replaces the Pod directly, avoiding devices such
as cEOS getting stuck after a stop signal. Every device sharing that Pod restarts with it.

See [Link wire semantics](/docs/guides/link-wire) for carrier, loss, MTU, and timing limits,
and [#344](https://github.com/clabernetes/clabernetes/pull/344) for non-live link recovery.

## Controllable management networking and a routed mesh

c9s now allocates management addresses before devices start. Choose IPv4 and IPv6 subnets,
gateways, and automatic allocation ranges through the containerlab `mgmt:` block in a Topology,
or `spec.mgmt` on a NodeProfile. Pin individual nodes with `mgmt-ipv4` / `mgmt-ipv6`; automatic
allocation works around pinned addresses and rejects duplicates or gateway collisions.
Without an override, IPv4 uses `172.20.20.0/24`; IPv6 allocation requires an IPv6 subnet.

For example, this block inside a containerlab definition selects a subnet and limits automatic
allocation to part of it:

```yaml
mgmt:
  ipv4-subnet: 10.20.30.0/24
  ipv4-gw: 10.20.30.1
  ipv4-range: 10.20.30.128/25
```

Devices in the namespace reach each other's management addresses across Pods and workers,
with peer source addresses preserved. Node names, aliases, and chassis component names resolve
to management addresses inside devices, so telemetry collectors, syslog targets, and tools can
use the same names and addresses as a local containerlab lab. Membership and Pod-address changes
propagate through a shared peer directory without restarting the other devices. Updates depend
on kubelet ConfigMap projection and are not instantaneous.

The mesh routes traffic over a dedicated management tunnel. Proxy ARP and IPv6 neighbor
discovery provide peer reachability without flooding traffic or using DNS for discovery.
IPv4 neighbor and forwarding entries are installed on demand; contacting every peer can still
produce all-to-all state. IPv6 proxy entries track the IPv6 peers. Each Pod answers its own
management gateway, and traffic outside the management subnet leaves through ordinary Pod
networking. Other management broadcasts and multicasts, such as DHCP, LLDP, and mDNS, stay
inside the Pod.

### Turning management off

For labs that only need Pod networking and their declared data links, set
`spec.disableManagement: true` on the Topology, or `spec.mgmt.disabled: true` on its NodeProfile.
This disables management address allocation and the c9s mesh. Omit explicit node management
addresses; management-subnet reachability and peer names are unavailable in this mode. Kinds
that require a configured management interface may still need the overlay enabled.

Management MTU handling and TCP MSS clamping also improve portability across cluster networks,
including vCluster/Talos. The sidecar keeps its transport ports reachable through device-installed
nftables firewalls, including cEOS policies, while the device continues filtering its own traffic.

See the [management network guide](/docs/guides/management-network) and
[management opt-out](/docs/concepts/containerlab-differences). Related changes:
[#315](https://github.com/clabernetes/clabernetes/pull/315),
[#317](https://github.com/clabernetes/clabernetes/pull/317),
[#325](https://github.com/clabernetes/clabernetes/pull/325),
[#338](https://github.com/clabernetes/clabernetes/pull/338), and
[#343](https://github.com/clabernetes/clabernetes/pull/343).

## Saved configuration survives Pod replacement

With persistence enabled, the startup configuration seeds the device once. Configuration the
device subsequently saves survives Pod replacement, eviction, and unrelated topology edits.
Preparation preserves device-modified files while continuing to update planned files the device
has not changed. This applies to full-file and CLI-format startup configurations.

- `enforce-startup-config: true` makes the declared startup configuration win again on each boot.
- A new `c9s.run/device-state-reset` Node annotation replaces the Pod and resets its persisted
  artifact tree once per token; the `DeviceStateReset` condition reports progress.
- `persistence.reclaim: Retain` keeps the PVC after Node or Topology deletion, allowing a
  recreated Node to adopt its saved state. The default remains `Delete`.
- New claims default to 512Mi. Increase the size for devices storing larger artifacts or logs.

Persistence remains opt-in. Without it, Pod replacement loses saved device state. See
[Persistent storage](/docs/guides/persistence) and
[#331](https://github.com/clabernetes/clabernetes/pull/331).

## Planning and startup at scale

The Helm chart starts four reusable planner workers by default. Each request runs in a fresh
subprocess with a private workspace, preserving node-specific identities and certificates.
`plannerPool.replicas` controls capacity; `plannerPool.enabled: false` selects disposable
planning Pods. Pool requests have a five-minute execution limit and a 64MiB aggregate payload
limit; use the disposable path for larger payloads. Increasing the pool beyond the controller's
16 concurrent Node reconciles requires a controller change.

Two optional controls pace large deployments through `Config.spec.rollout` installation-wide
and `Topology.spec.rollout` per lab:

| Setting | What it limits | When the next work starts |
| --- | --- | --- |
| `batchSize` | New primary Pod groups admitted together | After the admitted Pods have network-ready sandboxes |
| `maxConcurrentPerHost` | Device boots on each Kubernetes worker | After a primary device container passes its startup probe |

Both scopes apply when configured; zero or omission disables the corresponding limit. Groups
sharing a Pod count once. Admission survives manager restarts, and policy changes do not restart
existing devices. Batch admission does not wait for full link readiness, which may depend on a
later batch. Per-host startup probes should likewise check local startup rather than later peers.

The controller reuses successful reconciliations, indexes ConfigMap/Secret dependencies, and
coalesces peer-directory and progress updates. The connectivity helper distinguishes local
startup from full peer readiness: a delayed peer keeps the device unready without repeatedly
restarting a healthy helper. Optional `manager.diagnostics: true` exposes loopback-only metrics
and pprof for access through port forwarding.

In the recorded seven-worker, dual-stack Calico experiment, 1,000 BusyBox devices reached
Topology Ready in 5m15s with the combined optimizations and batches of 100, versus 13m10s in the
earlier unrestricted run. This is a workload-specific result, not an isolated batching speedup
or a vendor-device guarantee: at 200 devices, unrestricted startup was faster than batching.
See [Measuring large topology startup](/docs/guides/scaling-performance) for conditions and
limits, [#343](https://github.com/clabernetes/clabernetes/pull/343) for admission and controller
changes, and [#346](https://github.com/clabernetes/clabernetes/pull/346) for planner reuse and
linked-lab validation.

## Registry access and Service exposure

The controller can resolve image metadata through registry mirrors, including Harbor proxy
projects with path rewriting, using `Config.spec.imagePull.registryMetadataMirrors`.
`registryMetadataTrust` configures private CAs or HTTP for those metadata connections. Image
references retain their original identity; worker container-runtime mirror and trust settings
still control kubelet pulls. A failed configured mirror fails planning without falling back to
the public registry. Missing or unreadable pull Secrets now produce explicit Node conditions,
and planning recovers when the Secret becomes readable. See [Image pulling](/docs/guides/image-pull),
[#324](https://github.com/clabernetes/clabernetes/pull/324), and
[#326](https://github.com/clabernetes/clabernetes/pull/326).

Expose Services now carry application-protocol hints for familiar management ports. Override
or suppress a hint with `Node.spec.appProtocols`, or the `c9s.run/appProtocols` label inside a
containerlab definition. These hints describe endpoints; they do not open additional ports or
configure the device. See [Application-protocol hints](/docs/guides/expose-configuration#application-protocol-hints)
and [#339](https://github.com/clabernetes/clabernetes/pull/339).

LoadBalancer Services can request either pinned or automatically allocated management addresses,
so devices can be exposed at their management IP without pinning every node. This changes the
behavior of `useNodeMgmtIpv4Address` / `useNodeMgmtIpv6Address`; see the pool requirements in
[Breaking API changes](#breaking-api-changes) and
[#347](https://github.com/clabernetes/clabernetes/pull/347).

## Expanded node vocabulary

The Node spec and Topology compiler accept more of the native containerlab vocabulary:
`startup-delay`, `restart-policy` (`always`/`unless-stopped`), `image-pull-policy`, `cpu` and
`memory` (device-container limits), `healthcheck` (merged over the image OCI healthcheck),
`aliases` (extra same-namespace Service names for the node's Pod), `link-apply-mode`, `group`,
and `topology.groups` inheritance. Compilation is fail-closed: vocabulary the direct runtime
deliberately rejects fails with a diagnostic stating why, and only cosmetic Docker-only
constructs are accepted with warnings. See
[Differences from containerlab](/docs/concepts/containerlab-differences).

## Compatibility and clearer failure reporting

- Topology compilation sanitizes names Kubernetes cannot carry, such as uppercase node names,
  while rejecting collisions. Conflicting child resource names are detected before creation,
  and reserved container mount paths fail with a diagnostic naming the path.
- Failed topology `exec` commands are logged without putting an otherwise running device into
  a crash loop. Grouped nodes can share identical payloads and image-derived ports; explicit
  port collisions still fail planning.
- Topology status uses a status subresource, so reporting progress no longer overwrites spec
  defaults. `status.observedGeneration` lets clients distinguish readiness for the current
  definition, and Node readiness is invalidated when relevant inputs change.
- Deployment apply failures, rejected plans, and artifact-name conflicts are visible on the
  Node instead of only in manager logs. SSH probe passwords that coincide with declared or
  generated device defaults no longer cause false plan rejection; other Secret values remain
  screened from plan artifacts.
- A new [Cumulus VX example](https://github.com/clabernetes/clabernetes/blob/main/examples/basic/cumulus-multitool.yaml)
  and opt-in e2e suite cover deployment and connectivity with a Linux peer.

## Breaking API changes

The `LauncherProfile` CRD is renamed to `NodeProfile` (`Node.spec.profileRef`,
`Node.status.appliedProfile`); it carries reusable direct-workload
policy (expose, scheduling, resources, persistence, probes, image pull). Device privilege and
kind-owned container requirements come from the imported package plan.

Launcher-era fields are removed from `Config`, `NodeProfile`, and `Topology`: launcher
image/log/env settings, `privilegedLauncher`, containerlab debug/timeout/version, Docker
config and daemon config, insecure registries, pull-through, CRI overrides, by-kind resource
defaults, and Docker management-network fields. `Link.status.error` is replaced by the
`Accepted` condition, `Link.status.tunnelID` becomes `Link.status.wireID`, and
`Node.status.probeStatuses` is removed. Per-node wire discovery Services use `<node>-wire`
instead of `<node>-vx`.

`disableExpose` is removed from Topology and NodeProfile. Replace `disableExpose: true` with
`spec.expose.exposeType: None`; wire and alias Services are unaffected. See
[#333](https://github.com/clabernetes/clabernetes/pull/333).

Two global settings that no longer controlled anything are also gone: the Topology and Config
`naming` fields and the Config `inClusterDNSSuffix` field, together with the
`globalConfig.naming` and `globalConfig.inClusterDNSSuffix` Helm values. Generated resources
are named after the containerlab node inside the Topology namespace, and services resolve
without a configurable suffix. Drop the fields from manifests and values files before
installing; a manifest that still sets them is rejected by the new schemas. See
[#335](https://github.com/clabernetes/clabernetes/pull/335).

Two node-definition fields change meaning:

- `ports` entries are destination ports only (`22/tcp`). The Docker-style `host:container`
  form is rejected on Nodes, and two-sided entries inside a Topology `definition:` are
  normalized to their destination port. c9s allocates the service side and records both halves
  in `Node.status.exposedPorts`.
- `labels` in a Topology `definition:` become Kubernetes labels on the emitted Node, its
  Deployment, and Pods; there is no `Node.spec.labels`. c9s-owned labels move to the qualified
  `c9s.run/` namespace. The old `clabernetes/...` label keys are no longer written or selected,
  while annotation keys keep their existing names.

`useNodeMgmtIpv4Address` and `useNodeMgmtIpv6Address` now request the node's management address
as the LoadBalancer IP whether the address is pinned or allocated. In 0.8, containerlab allocated
unpinned addresses inside the launcher Pod, so these options read only a pinned `mgmt-ipv4` or
`mgmt-ipv6`, and unpinned nodes got an IP chosen by the LoadBalancer provider. c9s now allocates
every management address itself, and the Service requests the address reported in
`Node.status.directManagement`. If you enable either option, pin only some nodes, and your
address pool covers only the pinned addresses, pin the remaining nodes or set `ipv4-range` so
allocated addresses fall inside the pool; otherwise their Services stay pending. See
[Service exposure](/docs/guides/expose-configuration#using-management-ips).

### Removed node vocabulary

The Node spec carries only the vocabulary the direct runtime can realize. Unknown fields are
rejected at apply time, and a Topology `definition:` fails compilation with a diagnostic naming
each unsupported field and its location.

| Removed | Use instead |
| --------- | ------------- |
| `publish`, `sandbox`, `kernel`, `wait-for`, top-level `SANs` | Nothing, containerlab itself removed these. `SANs` moved to `certificate.sans` |
| `runtime` | Nothing, devices run as regular Kubernetes containers |
| `auto-remove` | Nothing, Kubernetes owns container lifecycle |
| `pid-mode`, `cgroupns-mode` | Nothing, these Docker namespace-sharing modes have no Pod mapping |
| `cpu-set` | Use `cpu`/`memory` limits; CPU pinning has no portable Pod mapping |
| `credentials` | Referenced Secrets; imported kind default credentials still apply |
| `stages` | Nothing, stage ordering assumes the whole lab on one host |
| `labels` | `metadata.labels` on the Node, automatic in a Topology `definition:` |
| `position` | Nothing, it feeds containerlab graphs, which c9s does not produce |
| `extras.mysocket-proxy` | Nothing, mysocketctl is gone along with the `publish` field that fed it |

## Upgrading from 0.8

All c9s custom resources now use `apiVersion: c9s.run/v1alpha1` instead of
`clabernetes.containerlab.dev/v1alpha1`. There is no automatic migration of existing custom
resource instances; treat this as a clean cutover. Uninstalling c9s deletes all Topology, Node,
Link, NodeProfile, and Config resources when the CRDs are removed.

1. Export your manifests before uninstalling:

   ```bash
   kubectl get topologies,nodes,links,launcherprofiles,configs -A -o yaml > backup.yaml
   ```

2. Uninstall the existing c9s install and remove its CRDs:

   ```bash
   make uninstall
   ```

   Or manually uninstall the Helm release, delete all `*.c9s.run` and
   `*.clabernetes.containerlab.dev` CRDs, then delete the `c9s` namespace.

3. Update every manifest to the new API group (`apiVersion: c9s.run/v1alpha1`), rename
   `kind: LauncherProfile` to `kind: NodeProfile` and `Node.spec.launcherProfileRef` to
   `Node.spec.profileRef`, and remove any field listed above.

4. Install the new c9s release (Helm install).

5. Re-apply your updated manifests.

The repository `make install` target performs the API-group check before Helm. It allows
same-group version changes, but refuses a legacy/new group crossing and prints the destructive
cleanup command. With `kubectl`, the fully qualified resource names change accordingly, for
example `kubectl get nodes.clabernetes.containerlab.dev` becomes `kubectl get nodes.c9s.run`.

Rolling back after the CRD replacement means reinstalling the prior release with its matching
CRDs and restoring the backed-up resources.

## Build, documentation, and tooling

Supported kinds come from the imported containerlab 0.79.0 registry. c9s maintains no kind
catalog of its own, and a containerlab module bump admits newly registered kinds without c9s
changes.

ARM image builds are fixed ([#302](https://github.com/clabernetes/clabernetes/pull/302)), and
the project moves to Go 1.26 ([#305](https://github.com/clabernetes/clabernetes/pull/305)).
Documentation expands installation, global configuration, registry access, persistence, and
architecture guidance ([#334](https://github.com/clabernetes/clabernetes/pull/334)), with updated
examples, interactive diagrams, YAML views, and branding. Preview builds update their existing
PR comment ([#349](https://github.com/clabernetes/clabernetes/pull/349)); documentation checks
also run according to changed files.

Contributor maintenance includes OpenSpec workflow updates
([#332](https://github.com/clabernetes/clabernetes/pull/332)) and CI action upgrades for pnpm,
PR comments, uv, and Node.js ([#327](https://github.com/clabernetes/clabernetes/pull/327),
[#328](https://github.com/clabernetes/clabernetes/pull/328),
[#329](https://github.com/clabernetes/clabernetes/pull/329),
[#330](https://github.com/clabernetes/clabernetes/pull/330)).
