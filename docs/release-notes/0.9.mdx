<Callout type='warn'>

This release replaces the nested launcher runtime with the direct device runtime and removes
launcher-era API fields. Upgrading is destructive: back up your resources and plan a full
uninstall and reinstall. There is no in-place `helm upgrade` path and no nested-runtime
fallback in this release.

</Callout>

## The direct device runtime

Every network device now runs as a regular application container in a c9s-managed Pod. The
launcher image, the Docker daemon inside the Pod, the containerlab executable, image import,
and nested container discovery are gone. What this changes in practice:

- `kubectl logs`, `kubectl exec`, resource limits, and Pod status address the *actual* device
  container. Chassis cards and grouped nodes are visible application containers of one Pod.
- The kubelet performs the only image pull, with native `imagePullPolicy` and
  `imagePullSecrets`. c9s resolves only registry metadata (manifests and config blobs) and
  fails readiness if the running image diverges from the planned digest.
- Kind behavior comes exclusively from the pinned containerlab 0.78.0 Go module, executed in
  short-lived locked-down planning Pods that record a deterministic device plan. A containerlab
  module bump admits newly registered kinds without c9s code changes.
- Each device Pod boots through a preparation init container (stages and digest-verifies every
  generated and payload artifact) and a restartable privileged connectivity init-sidecar that
  gates device start on the accepted cold-start interface set and reconciles live Link changes.

## Connectivity realization

Each device Pod's privileged connectivity sidecar realizes its own links; no node-resident agent
is installed. Cross-Pod wires terminate on in-Pod VXLAN VTEPs keyed by the Link's cluster-wide
tunnel id, while same-Pod, loopback, and local veth state stays inside the Pod sandbox. The device
always sees a plain veth interface. Wire semantics -- L2 point-to-point, MTU intent, live rewires,
cleanup, rescheduling -- are unchanged. The `connectivity` field is removed from Topology and Link
specs (there is exactly one realization; the experimental slurpeeth transport is retired).

## The management network is one L2 domain

The management subnet spans the whole topology as a single broadcast domain, matching
containerlab's management network: devices reach each other's *management addresses*
device-to-device -- hardcoded telemetry targets, syslog collectors, and plain ping across Pods
all work -- while the management gateway stays strictly Pod-local with one deterministic
identity. Peers are discovered through a namespace-scoped headless Service and converge on the
sidecar's reconcile tick, so nodes joining or leaving never restart other Pods.

## Expanded node vocabulary

The Node spec and Topology compiler accept more of the native containerlab vocabulary:
`startup-delay`, `restart-policy` (`always`/`unless-stopped`), `image-pull-policy`, `cpu` and
`memory` (device-container limits), `healthcheck` (merged over the image OCI healthcheck),
`aliases` (extra same-namespace Service names for the node's Pod), `link-apply-mode`, `group`,
and `topology.groups` inheritance. Compilation is fail-closed: vocabulary the direct runtime
deliberately rejects (`runtime`, `auto-remove`, `pid-mode`, `cgroupns-mode`, `cpu-set`,
`stages`, `credentials`) fails with a diagnostic stating why, and only cosmetic Docker-only
constructs are accepted with warnings.

## Breaking API changes

The `LauncherProfile` CRD is renamed to `NodeProfile` (`Node.spec.profileRef`,
`Node.status.appliedProfile`); its spec is unchanged and carries reusable direct-workload
policy (expose, scheduling, resources, persistence, probes, image pull). Device privilege and
kind-owned container requirements come from the imported package plan.

Launcher-era fields are removed from `Config`, `NodeProfile`, and `Topology`: launcher
image/log/env settings, `privilegedLauncher`, containerlab debug/timeout/version, Docker
config and daemon config, insecure registries, pull-through, CRI overrides, by-kind resource
defaults, and Docker management-network fields. `Link.status.error` is replaced by the
`Accepted` condition, and `Node.status.probeStatuses` is removed. See
[Upgrading](/docs/upgrading) for the complete field disposition table.

Rollback after the CRD replacement means reinstalling the prior release with its matching CRDs
and restoring backed-up resources; the direct runtime deliberately contains no nested emergency
path.

## Compatibility

Per-kind compatibility is generated from the live imported registry and the recorded
conformance evidence -- see [Compatibility](/docs/compatibility). A kind is reported compatible
only while its planning, boot, management, dataplane, lifecycle, and cleanup evidence is
current; evidence is invalidated automatically when the baseline, planner, renderer,
preparation, or connectivity implementation changes.
